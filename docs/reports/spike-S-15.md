# Спайк S-15 — SQLite на 100 000 треков

- **Дата:** 2026-10-16, Этап 0 · **Задача:** T0.21 · **Бюджеты:** P-08 (страница 100 строк ≤ 10 мс), P-09 (поиск p95 ≤ 80 мс) — `08` §1
- **Вопрос:** держит ли схема `03` §7 (широкая строка трека с блобами анализа) и поиск `05` §11 (FTS5 + триграммы + Дамерау–Левенштейн) масштаб 100 000 треков без денормализации.

## 1. Что сделано
Код: `spikes/S-15-sqlite/` (`rusqlite` 0.40 bundled → SQLite 3.53.2, вне workspace).
- Синтетика (детерминированная): 100 000 треков, 10 000 исполнителей, 15 000 альбомов; названия из русских и английских слов; 1/8 треков с фитом. У каждого трека блобы реального размера: `peaks` 400 Б, `env_head/env_tail` по 300 Б, `embedding` 68 Б, `fingerprint` ~900 Б.
- Прагмы — как в `03` §7: WAL, `synchronous=NORMAL`, `mmap_size` 256 МБ, кэш 64 МБ.
- Страницы — keyset-пагинация по покрывающим индексам, 1 000 страниц подряд по всей медиатеке.
- Поиск — ровно по `05` §11: префиксный FTS5 с весами bm25 (название 4, исполнители 5, альбом 2, жанр 1, псевдонимы 1) → при < 5 результатах триграммы (`OR` триграмм запроса) → перерасчёт Дамерау–Левенштейна ≤ 2 по топ-200; затем загрузка 50 строк для показа.

Окружение: Ryzen 7 5800H, NVMe, Windows 11 10.0.26300, release.

## 3. Выводы
- **P-08 и P-09 выполнены с запасом ×10 и ×5** — схема `03` §7 без денормализации; индексы `(title_norm, id)`, `(added_at DESC, id)` добавить в миграцию `0001` (в `03` §7 есть только `ix_track_added`).
- Блобы анализа в строке трека не мешают страницам (покрывающие индексы), но дают основную часть размера БД. Если размер станет проблемой — вынести `fingerprint`/`env_*` в отдельную таблицу (решение не нужно сейчас).
- Самая медленная ветка — опечатки (DL в Rust по 200 кандидатам); при необходимости — ограничить DL токенами ≥ 5 символов (уже) и кандидатами ≤ 100.

## 4. Не проверено
- Запись во время чтения (импорт в фоне + прокрутка) — проверим на реальном импорте (T1.x), WAL это допускает.
- HDD/флешка (`journal_mode=DELETE` для съёмных носителей) — у владельца.
