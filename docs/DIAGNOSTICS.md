# Диагностика SirTone

Статус: Windows foundation D-180 и iOS-реализация в исходниках. Формат, экспорт и добровольная отправка через настроенный HTTPS Feedback API работают; iOS требует macOS-сборки и ручной проверки устройства.

## Принципы

- Диагностика не является телеметрией: ничего не передаётся без явного действия пользователя. Переключатель вложения выключен по умолчанию.
- Installation ID — случайный UUID для этой установки; Session ID — новый UUID на каждый запуск; Report ID — UUID каждого ZIP.
- Не используются MAC-адрес, serial number, Apple ID или аппаратный fingerprint.
- Незакрытый маркер прошлой сессии означает только отсутствие штатного выхода. Это не утверждение о crash.
- Любая запись JSONL выполняется вне audio RT-path. В callback аудио запрещены файловые операции, mutex, форматирование и аллокации.

## Что хранится локально

`%LOCALAPPDATA%\SirTone\diagnostics` (или portable/Test data-dir) содержит Installation ID, маркер сессии и JSONL-файлы `events-YYYY-MM-DD.jsonl`.

Разрешённые поля события: версия схемы, UTC-время, уровень, event ID, Session ID, платформа, версия/Build ID, канал, компонент, операция, код ошибки, безопасный контекст и recoverable. Контекст имеет allow-list: попытка, тип аудиоустройства, тип ошибки, состояние сети/операции, задержка повтора. Значения приводятся к коротким техническим атомам.

Уже фиксируются `APP_STARTED`, `APP_STOPPED`, `PREVIOUS_SESSION_UNCLEAN`, сбой запуска аудиодвижка (`AUDIO_ENGINE_INIT_FAILED`), ошибки движка воспроизведения (`PLAYBACK_ENGINE_ERROR`), B0-анализа (`ANALYSIS_B0_FAILED`), проверки/скачивания обновления (`UPDATE_CHECK_FAILED`) и добровольная отправка (`FEEDBACK_SENT`). Обычный `AppError` в этом журнале сохраняется только как стабильный `ErrorCode`: его свободные `details` не попадают ни в JSONL, ни в ZIP. Ошибки движка передаются через ограниченный неблокирующий канал в отдельный поток записи; аудиоколбэк не выполняет запись на диск.

Срок обычных событий — до 7 дней; общий объём — до 10 МБ. Повреждённые строки JSONL пропускаются при экспорте.

В события и экспорт не попадают музыка, база медиатеки, имена треков, полные пути, история, предпочтения, Apple ID, пароли, токены и HTTP authorization headers.

На iOS эти же данные находятся в Application Support `SirTone/diagnostics`. Переход приложения в background завершает текущую сессию, а возвращение начинает новую; это не является самодельным перехватом native crash. Для символикации настоящих native crash понадобятся dSYM и внешний разрешённый сервис/Apple-инструменты после решения владельца.

В iOS-форме ZIP подготавливается до HTTPS-запроса. Если запрос не удался, введённый черновик и ссылка на этот же локальный ZIP остаются в форме: пользователь может повторить отправку, открыть Share Sheet или воспользоваться системным Mail, не создавая другой отчёт.

На iOS «Настройки» → «Помощь и обратная связь» → «Сбросить диагностические данные» удаляет локальный JSONL-журнал и Installation ID после явного подтверждения. Экспортированные ранее ZIP остаются в каталоге отчётов, а музыка и база медиатеки не затрагиваются.

## Экспорт отчёта

В Windows: «Настройки» → «Помощь и диагностика» → «Сохранить отчёт». Файл создаётся локально в `reports` data-dir с именем `sirtone-report-<Report ID>.zip` и не превышает 5 МБ. В форме «Сообщить об ошибке» или «Предложить улучшение» пользователь может отдельно включить вложение и отправить его через HTTPS API. Если форма открыта из уведомления ошибки воспроизведения, к обращению автоматически привязывается только безопасный код ошибки; пути, имена треков и прочие личные данные при этом не добавляются. При отсутствии endpoint черновик и ZIP остаются локально.

ZIP содержит:

- `summary.txt` — короткое резюме; при включённом пользователем диагностическом вложении к обращению оно также содержит его описание проблемы;
- `manifest.json` — версия формата и идентификаторы;
- `environment.json` — ОС и архитектура;
- `events.jsonl` — события последних 24 часов;
- `errors.json` — ошибки из выбранного окна событий;
- `README.txt` — ограничения состава.

Архив сначала полностью записывается во временный файл и синхронизируется с диском; под итоговым именем он появляется только после успешного атомарного переименования. Ошибка прав или места на диске не выдаётся за созданный отчёт и не заменяет существующий файл.

При превышении лимита сохраняются более новые события, а manifest/summary помечают усечение. При отправке с вложением этот же Report ID используется в API-запросе и письме поддержки. Архив не отправляется автоматически и не распаковывает недоверенные ZIP.

## Разработчику

Автоматические тесты `diagnostics` проверяют идентификаторы, маркер сессии, ротацию, повреждённый JSONL, состав ZIP и отсутствие подставленных пути/токена. Уровень developer logging по-прежнему задаётся `SIRTONE_LOG`; он не меняет allow-list экспортируемых событий.

В Windows «Настройки» → «Помощь и диагностика» → «Сбросить диагностический идентификатор» удаляет только эту папку и сразу создаёт новый Installation ID; музыка и база медиатеки не затрагиваются. Тот же результат вручную: закройте SirTone и удалите только папку `diagnostics` в data-dir.
